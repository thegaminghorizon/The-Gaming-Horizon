## ✦ Browser-First Boundary

The project should not be casually described as:

```text
CLOUD GAMING

GAME STREAMING

REMOTE GAME EXECUTION

DESKTOP GAME LAUNCHER

GAME DOWNLOAD CLIENT

QUEUE-BASED STREAMING PLATFORM
```

unless the project's formal direction changes.

The official Gaming Horizon launch date is:

```text
1 JANUARY 2027
```

Written form:

```text
1 January 2027
```

Conflicting dates should be corrected rather than propagated.

<a id="documentation-principles"></a>

## ✦ Documentation Principles

### `01` — Explain Purpose

Every major document should explain why its system exists.

---

### `02` — Separate Current From Future

Do not blur implementation and possibility.

---

### `03` — Document Systems, Not Just Files

Documentation should explain relationships and responsibilities.

---

### `04` — Use Stable Navigation

Documents should link clearly to related systems.

---

### `05` — Preserve Project Truth

Never invent facts to make documentation look more complete.

---

### `06` — Prefer Clarity Over Complexity

Documentation should make the project easier to understand.

---

### `07` — Use GitHub-Safe Diagrams

Static diagrams and tables should remain readable directly in Markdown.

---

### `08` — Do Not Invent Metrics

Use numbers only when real project measurements exist.

---

### `09` — Keep Relative Paths Correct

Documentation should remain usable from its actual repository location.

---

### `10` — Keep Security Information Safe

Documentation must not expose secrets or sensitive operational information.

---

### `11` — Update Connected Documents

A meaningful change may affect more than one document.

---

### `12` — Documentation Evolves With the Horizon

Docs are part of the system, not an afterthought.

---

- [ ] Relative links are correct
- [ ] Repository URLs use the correct repository
- [ ] Official network destinations are correct
- [ ] No invented metric is introduced
- [ ] No unsupported partnership is implied
- [ ] No unsupported technology is claimed
