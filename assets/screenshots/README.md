<a id="overview"></a>

## ✦ Overview

The Gaming Horizon screenshot system documents the visual state of real
Gaming Horizon interfaces and product experiences.

It provides a structured home for interface captures used across:

- repository documentation;
- product explanation;
- feature documentation;
- development communication;
- website references;
- developer documentation;
- support documentation;
- roadmap communication;
- GitHub presentation;
- future release documentation.

Screenshots are evidence of interface presentation.

They should therefore be treated differently from conceptual or cinematic
showcase artwork.

> [!IMPORTANT]
> A screenshot should communicate what Gaming Horizon actually displays,
> not what an unrelated concept imagines it could display.

<a id="version"></a>

## ✦ Version

Current screenshot-system version:

```text
1.0.0
```

Version structure:

```text
MAJOR.MINOR.PATCH
```

### Major

Used when the screenshot architecture or documentation system changes
significantly.

Example:

```text
1.0.0 → 2.0.0
```

Possible reasons:

```text
Major directory redesign
New screenshot classification architecture
Complete product-documentation restructuring
Major governance change
```

### Minor

Used when meaningful new screenshot groups or documentation categories are
introduced.

Example:

```text
1.0.0 → 1.1.0
```

Possible reasons:

```text
New mobile screenshot category
New dashboard screenshot system
New release-history gallery
New accessibility-state captures
```

### Patch

Used for smaller documentation refinements.

Example:

```text
1.0.0 → 1.0.1
```

Possible reasons:

```text
Filename correction
Relative-path fix
README improvement
Metadata adjustment
Classification correction
```

<a id="classification"></a>

## ✦ Screenshot Classification

Every screenshot should be understandable in context.

Recommended classifications:

| Classification | Meaning |
| --- | --- |
| `CURRENT` | Represents a current interface |
| `DEVELOPMENT` | Captured during active development |
| `PREVIEW` | Represents a preview experience |
| `EXPERIMENTAL` | Represents an experimental interface |
| `ARCHIVED` | Historical product reference |
| `REPLACED` | Superseded by a newer screenshot |

The classification can be documented in surrounding Markdown rather than
embedded permanently inside the image.

<a id="product-states"></a>

## ✦ Product States

Gaming Horizon is actively evolving.

Screenshots may therefore represent different development states.

Use clear surrounding labels where necessary.

Recommended states:

```text
CURRENT
PREVIEW
IN DEVELOPMENT
EXPERIMENTAL
COMING SOON
AVAILABLE AT LAUNCH
ARCHIVED
REPLACED
```

Do not silently present an experimental or historical interface as the current
production experience.

---

## ✦ Screenshot vs Product Truth

A screenshot records:

```text
A VISUAL STATE
AT A PARTICULAR TIME
```

It does not automatically define:

```text
CURRENT PRODUCT POLICY
CURRENT RELEASE INFORMATION
CURRENT AVAILABILITY
CURRENT ROADMAP
CURRENT LEGAL STATUS
```

For changing information, current project documentation should remain the
authoritative source.

<a id="capture-standard"></a>

## ✦ Capture Standard

Before capturing a Gaming Horizon interface:

### `01` — Prepare the interface

Ensure the intended page or feature is fully visible.

### `02` — Remove distractions

Close unrelated overlays, browser notifications, developer tools, and temporary
system messages.

### `03` — Check data

Make sure no private information appears.

### `04` — Review state

Confirm the interface is in the intended product state.

### `05` — Capture cleanly

Preserve the intended proportions and resolution.

### `06` — Review

Inspect the final image before committing it.

---

## ✦ Browser Capture Standard

Where practical, avoid including:

```text
UNRELATED BROWSER TABS
PERSONAL BOOKMARKS
ACCOUNT PROFILE MENUS
BROWSER DOWNLOADS
SYSTEM NOTIFICATIONS
DESKTOP CONTENT
PRIVATE EXTENSIONS
DEVELOPER TOOLING
```

unless the browser frame itself is intentionally part of the documentation.

---

## ✦ Cropping

Crop only when doing so improves focus without removing meaningful context.

Good crop:

```text
REMOVES EMPTY OR UNRELATED AREA
PRESERVES COMPLETE FEATURE
MAINTAINS UNDERSTANDABLE CONTEXT
```

Bad crop:

```text
REMOVES IMPORTANT CONTROLS
CUTS TEXT
HIDES PRODUCT STATE
DISTORTS THE INTERFACE
CREATES A MISLEADING IMPRESSION
```

---

## ✦ Aspect Ratio

Do not stretch screenshots.

Avoid:

```html
<img
  src="website/gaming-horizon-gateway.png"
  width="1000"
  height="300"
/>
```

unless those values preserve the original aspect ratio.

Prefer:

```html
<img
  src="website/gaming-horizon-gateway.png"
  width="100%"
  alt="Gaming Horizon Gateway"
/>
```

Official screenshots should be:

WELL ORGANIZED
SAFE TO PUBLISH

Capture at enough resolution that important UI remains readable.

Avoid screenshots that become unusable because of:

```text
HEAVY COMPRESSION

EXTREME UPSCALING
POOR CROPPING
```

| --- | --- |

| `PREVIEW` | Represents a preview experience |

| `EXPERIMENTAL` | Represents an experiment |
| `REPLACED` | Superseded by a newer capture |
| `ARCHIVED` | Preserved historical reference |

---

## ✦ Adding a Screenshot

Before adding a new screenshot:

1. Identify what it documents.
2. Decide whether it belongs in `website/` or `features/`.
3. Confirm a similar screenshot does not already exist.
4. Prepare a clean product state.
5. Capture at appropriate resolution.
6. Check privacy and sensitive information.
7. Check accuracy.
8. Use a descriptive filename.
9. Update this README if it becomes part of the official register.
10. Use a meaningful commit.

---

## ✦ Replacing a Screenshot

When an interface changes:

1. Compare the new and current capture.
2. Confirm the change is meaningful.
3. Capture the updated interface cleanly.
4. Recheck sensitive information.
5. Preserve the established filename when appropriate.
6. Update related documentation.
7. Verify rendered GitHub paths.
8. Archive the previous version only if historical value justifies it.

- [ ] Capture is readable
- [ ] Important UI is visible

- [ ] No sensitive information is visible
- [ ] No credentials are exposed
- [ ] Screenshot classification is understood
- [ ] Filename is descriptive
- [ ] Correct directory is used
- [ ] File size is reasonable
- [ ] Product presentation is truthful
- [ ] Alternative text can describe the image clearly
- [ ] Existing duplicate has been checked

Before publishing, ask:

### What does this screenshot document?

There should be a clear answer.

### Is this interface real?

If not, it belongs in showcase or concept documentation.

### Is the captured state still relevant?

If not, mark or archive appropriately.

### Could anything private be visible?

Review carefully.

### Does the filename explain the image?

If not, rename it.

### Does the image improve documentation?

If not, it may not need to be committed.
