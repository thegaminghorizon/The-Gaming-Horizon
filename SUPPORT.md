<a id="overview"></a>

## ✦ Overview

The Gaming Horizon support system exists to help users, community members,
contributors, developers, creators, and other participants reach the correct
support destination.

Support is not one channel for every type of problem.

Different concerns require different handling.

```text
QUESTION
   │
   ▼
WHAT KIND OF HELP?
   │
   ├────────────► GENERAL SUPPORT
   │
   ├────────────► TECHNICAL ISSUE
   │
   ├────────────► BUG REPORT
   │
   ├────────────► ACCOUNT HELP
   │
   ├────────────► COMMUNITY / MEMBER REPORT
   │
   ├────────────► MODERATION APPEAL
   │
   ├────────────► SECURITY REPORT
   │
   ├────────────► PRIVACY REQUEST
   │
   ├────────────► CONTRIBUTION HELP
   │
   └────────────► PARTNERSHIP / MEDIA INQUIRY
```

The objective is to route the issue correctly while requesting only the
information actually needed.

# SUPPORT CATEGORIES

<a id="categories"></a>

## ✦ General Support

General Support is appropriate when the issue does not clearly belong to a
more specialized category.

Examples:

```text
I AM NOT SURE WHERE TO ASK

I NEED HELP FINDING A FEATURE

I NEED SUPPORT ROUTING

I HAVE A GENERAL PLATFORM QUESTION

I NEED HELP UNDERSTANDING A PROCESS
```

---

## ✦ Account Help

Account-related support may include:

```text
SIGN-IN QUESTIONS

ACCOUNT ACCESS

PROFILE ISSUES

ACCOUNT-RELATED SETTINGS

ACCOUNT EXPERIENCE PROBLEMS
```

Do not send:

```text
PASSWORDS

2FA CODES

RECOVERY CODES

SESSION TOKENS

AUTHENTICATION TOKENS
```

Support should never require a user's password.

---

## ✦ Technical Support

Technical Support is appropriate for problems affecting expected platform
operation.

Examples:

```text
PAGE DOES NOT LOAD

INTERFACE DOES NOT RESPOND

EXPECTED ACTION FAILS

BROWSER-SPECIFIC PROBLEM

NAVIGATION ISSUE

FORM FAILURE

DISPLAY PROBLEM

FEATURE BEHAVES UNEXPECTEDLY
```

When requesting technical support, useful context may include:

```text
WHAT YOU WERE TRYING TO DO

WHAT HAPPENED

WHAT YOU EXPECTED

BROWSER

DEVICE TYPE

ROUTE / PAGE

NON-SENSITIVE SCREENSHOT

ERROR MESSAGE
```

---

## ✦ Bug Reports

A reproducible repository or application bug may belong in GitHub Issues.

Before reporting:

```text
SEARCH EXISTING ISSUES
       │
       ▼
DUPLICATE?
   ┌───┴───┐
   ▼       ▼
  YES      NO
   │       │
   ▼       ▼
ADD USEFUL OPEN NEW
CONTEXT    REPORT
```

Issue templates:

[`.github/ISSUE_TEMPLATE/README.md`](.github/ISSUE_TEMPLATE/README.md)

---

## ✦ Feature Requests

Feature requests should explain a real problem or opportunity.

```text
PROBLEM
   │
   ▼
USER NEED
   │
   ▼
PROPOSED DIRECTION
```

Avoid presenting speculative capabilities as already confirmed roadmap items.

Roadmap:

[`ROADMAP.md`](ROADMAP.md)

## ✦ Report a Member

Reports involving another community member should be handled through the
appropriate private reporting process.

Examples may include:

```text
HARASSMENT

THREATS

SCAMS

IMPERSONATION

SPAM

MALICIOUS LINKS

SERIOUS RULE VIOLATIONS
```

Do not publicly accuse another member when a private reporting route is
available.

Provide relevant evidence without exposing unrelated private information.

---

## ✦ Reporting Principles

```text
REPORT PRIVATELY

BE SPECIFIC

PROVIDE RELEVANT EVIDENCE

DO NOT EXAGGERATE

DO NOT EDIT EVIDENCE MISLEADINGLY

DO NOT HARASS THE REPORTED PERSON

DO NOT ORGANIZE PUBLIC PILE-ONS
```

False or intentionally abusive reports may themselves violate community rules.

---

## ✦ Moderation Appeals

A moderation appeal is a request for a moderation action to be reviewed.

An appeal should include:

```text
WHAT ACTION WAS TAKEN

WHEN IT OCCURRED

WHY YOU BELIEVE REVIEW IS APPROPRIATE

RELEVANT CONTEXT

ANY RELEVANT EVIDENCE
```

An appeal is not a guarantee that the original decision will be changed.

---

## ✦ Appeal Conduct

Appeals should remain:

```text
RESPECTFUL

CLEAR

FOCUSED

HONEST
```

Avoid:

```text
SPAMMING APPEALS

THREATS

HARASSMENT

EVADING MODERATION THROUGH ALT ACCOUNTS

PUBLIC PRESSURE CAMPAIGNS
```

Community conduct:

[`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md)

# SECURITY SUPPORT

<a id="security"></a>

## ✦ Security Vulnerabilities

Security vulnerabilities require different handling from ordinary technical
support.

Read:

[`SECURITY.md`](SECURITY.md)

Do **not** publish sensitive vulnerability details in:

```text
PUBLIC GITHUB ISSUES

PUBLIC DISCORD CHANNELS

PUBLIC SOCIAL POSTS

PUBLIC COMMENTS
```

Use a private reporting route whenever available.

---

## ✦ Security Examples

Potentially sensitive reports may involve:

```text
AUTHENTICATION BYPASS

AUTHORIZATION FAILURE

PRIVATE DATA EXPOSURE

SECRET LEAKAGE

SESSION EXPOSURE

PRIVILEGE ESCALATION

UNINTENDED ADMINISTRATIVE ACCESS

SECURITY-CONTROL BYPASS
```

These examples do not imply that such vulnerabilities currently exist.

---

## ✦ Security Reporting Flow

```text
SECURITY CONCERN
      │
      ▼
COULD PUBLIC DETAILS
ENABLE ABUSE?
      │
   ┌──┴──┐
   ▼     ▼
  YES    NO
   │     │
   ▼     ▼
PRIVATE  NORMAL
REPORT   SUPPORT /
         BUG ROUTE
```

# SUPPORT REQUEST QUALITY

<a id="request-quality"></a>

## ✦ Writing a Good Support Request

A useful support request answers:

```text
WHAT ARE YOU TRYING TO DO?

WHAT HAPPENED?

WHAT DID YOU EXPECT?

WHERE DID IT HAPPEN?

CAN IT BE REPRODUCED?

WHAT HAVE YOU ALREADY TRIED?
```

---

## ✦ Recommended Technical Request Format

```text
TITLE:
Short description of the problem

AREA:
Website / account / community / repository / other

WHAT I WAS DOING:
Describe the action.

WHAT HAPPENED:
Describe the actual result.

EXPECTED:
Describe the expected result.

STEPS:
1.
2.
3.

ENVIRONMENT:
Browser:
Device:
Page / Route:

EVIDENCE:
Non-sensitive screenshot or error message if useful.

ADDITIONAL CONTEXT:
Anything else relevant.
```

---

## ✦ Screenshots

Screenshots can help support, but inspect them before sending.

Remove or hide unrelated:

```text
EMAIL ADDRESSES

PRIVATE MESSAGES

AUTHENTICATION TOKENS

PERSONAL INFORMATION

ADMIN INFORMATION

PRIVATE ACCOUNT DETAILS

SECRET KEYS
```

# SUPPORT SAFETY

<a id="safety"></a>

## ✦ Support Safety Principles

Support systems should:

```text
MINIMIZE SENSITIVE INFORMATION

VERIFY BEFORE HIGH-IMPACT ACTIONS

AVOID CREDENTIAL COLLECTION

KEEP PRIVATE CASES PRIVATE

PREVENT IMPERSONATION

PROTECT REPORTERS

PROTECT UNRELATED USERS

MAINTAIN AUDITABLE DECISIONS WHERE PRACTICAL
```

---

## ✦ Impersonation

Be cautious of users claiming to be:

```text
STAFF

MODERATORS

DEVELOPERS

SUPPORT AGENTS

PARTNERS
```

Official identity should be verified through official Gaming Horizon systems
rather than trust based only on a username or direct message.

# RESPONSE EXPECTATIONS

<a id="response-expectations"></a>

## ✦ Response Timing

Gaming Horizon does not declare a fixed guaranteed response time in this

```text

SEVERITY

SUPPORT CAPACITY
```

```text

IMMEDIATE RESOLUTION
```

# SUPPORT QUALITY GATE

<a id="quality-gate"></a>

## ✦ Before Sending a Support Request

- [ ] Correct support category selected
- [ ] Problem described clearly
- [ ] Relevant context included
- [ ] Reproduction steps included where applicable
- [ ] Private information removed
- [ ] Credentials removed
- [ ] Screenshots checked for sensitive information
- [ ] Existing documentation reviewed where practical
- [ ] Existing GitHub issues checked where relevant
- [ ] Request remains respectful and focused

---

## ✦ Before Support Responds

Support handling should consider:

- [ ] Is this the correct support route?
- [ ] Is private handling required?
- [ ] Is more information actually necessary?
- [ ] Are credentials being requested unnecessarily?
- [ ] Is identity verification needed for a sensitive action?
- [ ] Is this actually a security concern?
- [ ] Is this actually a privacy request?
- [ ] Is another user involved?
- [ ] Are project claims being represented accurately?
- [ ] Does the response avoid promises that cannot be guaranteed?
